# AGENTS.md — lunarlog

This document is the operating guide and technical context for AI agents working in this repository.

## Project Overview

`lunarlog` is a privacy-first family menstrual-cycle tracking application built with Flutter, built around a Supabase account that syncs profiles across a household's devices and lets multiple guardians share a profile with distinct roles (`viewer`/`caregiver`/`co_parent`/`primary_guardian`) — sync and multi-guardian family collaboration are the product's priority and its differentiator, not an add-on. It supports one adult operator managing multiple family profiles (including minors). Local storage (a Drift/sqlite3 store behind a device-credential gate, relying on the OS's own at-rest protection rather than an app-managed cipher — see docs/ops/ios-export-compliance.md; the schema's version-by-version history lives in `lib/data/db/db.dart`'s schema-history doc comment, not in this guide) keeps the app working when the network doesn't; that is a reliability property, not the product's identity. Sign-in methods: email/password, native Google Sign-In (iOS and Android), native Apple Sign-In (iOS), or passwordless email (link or emailed code). Offline-first sync of `profiles` and `day_entries` into RLS-protected Postgres runs via the `sync_push` RPC (which also carries, per issue #130, the `day_entry_merge_events` disclosure rows both resolvers emit — server-side inside the same-date resolver branch, client-side from `LunarLogStorage._resolveSameDateConflicts` through the same push path — with a 30-day server-side retention purge in `enforce_retention()`); other capabilities include in-app account deletion (server rows, the account, an Apple revocation when applicable, then the device reset - issue #17) and JSON export, available to any operator with a profile from Settings → Your data (no account required; server data is included only when signed in), and Sentry crash reporting behind an allowlist scrubber. An unconfigured build (no `--dart-define`s) has no account section, no sync, no crash reporting, and no delete tile (export remains available) — a development configuration for iterating without cloud credentials, not a supported product mode. See [`docs/product/positioning.md`](docs/product/positioning.md) for the full positioning rationale (audience, the family-collaboration story, and what lunarlog deliberately does not do). Settings → Your data also restores from the app's own export file (`lib/domain/import/account_import.dart`, `lib/data/import/account_importer.dart`; issue #140) via `file_picker` — same no-account-required scope, additive merge, nothing overwritten or deleted.

Target platforms: iOS (iPhone first-class) and Android for the Flutter app, plus the web — where web means the React web client in [`webapp/`](webapp/) (issue #1249, epic #831: a signed-in thin client that keeps nothing at rest in the browser). The Flutter app does not build for the web: the legacy Flutter web build was taken offline by issue #1248 and its code (`web/`, the WASM database, the web dev banner, `LUNARLOG_WEB_SYNC`) was removed by issue #1257. Do not add it back; `test/architecture/dom_surface_test.dart` fails if `lib/` imports a browser-DOM library. Web sign-in (issue #1250) runs through the same-origin auth Worker (`webapp/worker/auth.ts`): the browser holds only the in-memory access token (supabase-js's `accessToken` option), the refresh token lives in the rotating `__Host-` HttpOnly Secure SameSite=Strict cookie, the PKCE verifier in its own short-lived Lax cookie, and every state-changing `/auth/*` route demands the app's `Origin` plus the `x-lunarlog-csrf` custom header. The webapp's tooling, nothing-stored guard, staging deploy, and CI are documented in [`webapp/README.md`](webapp/README.md).

First-party platform adapters exist on both sides of the `lunarlog/health` channel (`lib/data/health/ios_health_channel.dart`, `android_health_channel.dart`, `AppDelegate.swift`'s `HealthKitChannelHandler`, and Android's `HealthConnectAdapter.kt`). **Both platforms write (issue #1478):** the write direction (`lib/data/health/health_flow_write_service.dart` + `health_flow_write_coordinator.dart`, forward-only from the moment access is granted) runs on iOS and on Android. **What a pass sends is decided from what it has written (issue #1581), not from a time cursor.** The moment access was granted is a floor that never moves (`SettingsKeys.healthSyncWrittenThroughMs`; the key's name is from when it was a cursor), and a row is looked at when it was saved after it. Every record the store accepts is remembered in the device-local export ledger with its row's `updatedAt` (`HealthExportLedger`, read through `lib/data/health/health_export_memory.dart`). A pass works out what each row in scope should have in the store, sends what the ledger does not hold at the row's present version, and deletes what the ledger holds that the row no longer produces. So a record that could not be written (its type is switched off, or the write failed) is still due on the next pass, nothing is sent twice, and a row that turns up with an old time is not missed: one that arrives late from another device, or a spotting entry whose day stops being a bleed day. Three rules that are easy to break: only a write the store accepted may enter the ledger (`_remember` is the one way in for a day's or an observation's record); a delete is not sent while the record's type is off (`healthRecordDeletable`), because both native halves pass over a type they may not write and still answer allowed; and the floor is stamped with the clock rows are stamped with (`AppDependencies.localWriteClock`), not the device's own. Which platforms write is one answer, `AppConfig.healthSyncWritesOn` / `healthSyncWritePlatforms` in `lib/config.dart`, read by the composition root (which builds the write and tombstone coordinators from it) and by the Settings screen (which chooses the write copy from it) — nothing else may restate the list (`test/composition/health_write_gate_test.dart`). Android had the Kotlin write handlers and the manifest permissions long before #1478 but sat behind an iOS-only gate, so the app asked Health Connect for five write permissions and wrote nothing. What Android writes, each for the one bound profile only: `MenstruationFlowRecord` (flow; super heavy as Heavy; spotting inside a period as Light), one `MenstruationPeriodRecord` per period episode, `IntermenstrualBleedingRecord` (spotting between periods), `CervicalMucusRecord` (discharge tagged sticky, creamy, or egg white), `OvulationTestRecord` (peak as Positive), and `BasalBodyTemperatureRecord`. Health Connect has no symptom or mood types, so those are iOS-only, and the Android screen says so. Four things about the Android half that are easy to get wrong: (1) `permissionStatus` answers `notAsked` until this install has launched the permission request that carries the writes (a marker in the adapter's SharedPreferences, stamped with the install's first-install time so that a copy carried to another phone by device-to-device transfer does not count) — Android cannot tell never-asked from denied by the granted set, and the write pass stops on `denied` before its own authorization request, so answering `denied` on a fresh install meant the write path could never ask; (2) that status is decided on the **write** permissions only, so declining an optional read (Health Connect's "Access past data", background access) neither reads as denied nor blocks writes, while a missing write permission stops every write and shows as denied; (3) a period record's end is the last instant of its last day, because Health Connect counts a period's days from start date to end date inclusive (an end at the next midnight showed a one-day period as "day 1 of 2"); (4) the period record belongs to no single day entry, so the write pass alone writes and removes it (`_collectPeriods` / `_reconcilePeriodRecords`, remembered in the device-local export ledger as `HealthExportLedgerKind.period`). Its rules: episodes are derived from **hand-logged** bleed days only — a day imported from a health store never starts, extends or reshapes a period record, so an import writes nothing back, and the record's zone is always a hand-logged day's (an imported row carries a fixed-offset zone such as `UTC+02:00`, which `day_boundary.dart` cannot resolve); an episode has a record exactly when this device has exported at least one of its days and it is 30 days or shorter (Health Connect refuses more than 31 days of elapsed time); it is written with its true first day even if that day predates the cursor; every write's version is the write time, kept above the last version written; and an episode whose zone cannot be resolved is left alone rather than failing every pass. Two rules about asking, both from the review of #1478: the forward-only cursor is stamped only when `permissionStatus` reads `granted` after the request (neither native half's `allowed` means the writes were granted — iOS answers it when the sheet completes, Android when any permission was granted), and the Android adapter sets its asked-marker whenever it sees a write granted, so write access that was granted elsewhere and later removed reads `denied`. It also sets it on seeing any permission it requests granted while this install has never launched the import's own request (`HealthPermissionState.remembersWritesAsked`): until then a read can only have been granted on a sheet that showed the writes beside it (the single request builds before #1515 made) or in Health Connect's own settings, and someone who declined the writes there must not be shown the write sheet again. **There are two permission requests on Android (issue #1515), and "asked" is kept apart for each.** The write pass's (`requestWriteAuthorization`) still carries everything, the writes with the reads beside them, on the one sheet raised a moment after a profile is bound. The tap import's (`requestImportAuthorization`) asks for the two record reads and the two optional read extras and for no write permission, so tapping Import no longer puts the writes in front of someone who declined them; it is raised only when one of the two record reads is not granted (`HealthPermissionState.importMustAsk`: with both granted, Import raises nothing, so an extra left off is not asked for again on every tap), and it sets a marker of its own (`IMPORT_REQUEST_LAUNCHED_KEY`), never the write one. So `permissionStatus` (`HealthPermissionState.writeStatusFor`) is decided on the writes alone: neither the import's marker nor a read granted on the import's sheet makes it `denied`, because that would stop the write pass before its own request for someone who was never shown a write permission. The read side counts either request as asked, since both carry the reads. On iOS there is one request as before: `requestImportAuthorization` sends Swift `requestWriteAuthorization` (the platform fact `readAccessDisclosed` chooses), and HealthKit never re-asks for a type already answered. One thing Health Connect does that is easy to trip over (seen on Android 15): it drops a whole request, showing nothing, when any permission in it has been declined twice (`PermissionsActivity: App has at least one USER_FIXED permission, finishing!`), and the dropped request counts as another refusal of everything in it that is not granted. The pass also runs when the app returns to the foreground (`onAppResumed`), since the permission is granted or removed on Health Connect's own screens. Check what Health Connect holds only on a freshly opened screen: its "Data and access" page does not refresh when its task is brought back to the front, which is how a working write was once read as "nothing written". **The owner reversed the write-only posture in issue #781 ("it's a cycle tracking app"), and both halves of the read/import path have since shipped:** #217 added the Apple Health menstrual-flow import on iOS, and #458 added the Health Connect menstrual-flow + intermenstrual-bleeding import on Android (`lib/data/health/health_import_service.dart`'s `LocalHealthImportService`, the `HealthImportSource` port, and `HealthConnectAdapter.kt`'s `getChangesToken`/`getChanges` read with `dataOrigin` filtering and a change-token-expiry fallback (`ChangesPage.changesTokenExpired` in connect-client 1.1.0, not a thrown exception)). Both are user-initiated only, write into the one bound profile, never overwrite a hand-logged value, and exclude the app's own writes by source. A hand correction to an imported day counts as hand-logged (issue #1559). The day sheet keeps such a row's imported provenance, so `source` cannot tell her edit from the store's. An imported row's `sourceId` therefore says which of the store's records it was written from (`_recordKey` in `health_import_service.dart`): the sample id on iPhone, where a sample cannot be edited, and `<record id>@<lastModifiedTime in ms>` on Android, where Health Connect changes a record in place. The import adopts a different value for an imported day only when the store's record is not that one. Two things it must not use: the row's `updatedAt` (any edit moves it, a tag as much as a flow), and anything about what was logged (`sourceId` survives deletion, on the server and in every guardian's copy, so the flow must never be written into it). Every Apple Health pass reads the whole history, so without this her correction was put back on the next import. Since issue #992 the import is full-history — it pages through everything the health store makes available (`lib/domain/health/health_import.dart`'s `kHealthImportPageSize = 500`, with Health Connect's `READ_HEALTH_DATA_HISTORY` declared for it) rather than a fixed recent window — and since issue #993 the same import also runs prompt-free in the background (iOS: `HKObserverQuery` + `enableBackgroundDelivery` in `AppDelegate.swift`'s `HealthKitChannelHandler`; Android: the periodic `HealthBackgroundImportWorker.kt` pushing the trigger through the shared channel), gated inside `LocalHealthImportService.importInBackground` by the #153 binding guard, the #1215 first-import marker and a read-side OS-permission probe (it never prompts, and stops when the profile is unbound or the permission is not granted). That probe is `importPermissionStatus`, not the write-side `permissionStatus` (issue #1491: gated on the writes, the background import never ran for someone who allowed reading and not writing). On Android it answers from Health Connect's granted set for the two record reads the import performs (`READ_MENSTRUATION` and `READ_INTERMENSTRUAL_BLEEDING` — not "Access past data", and not the background read, which `HealthBackgroundImportWorker` checks natively before it wakes Dart), and it reads the adapter's asked-markers without ever setting one, so it cannot change what `permissionStatus` answers for the write path. On iOS HealthKit never discloses read access, so `IOSHealthChannel` (`readAccessDisclosed: false`) answers it in Dart from the write types and no such method reaches Swift; an iPhone that may read but not write therefore still runs no background import, and the screen copy says so (`healthSyncWriteForwardOnly`). The Health sync screen's status line (issue #1515) is decided by the pure `healthAccessState` in `lib/domain/health/health_access_state.dart` from both answers: on Android someone who allowed reading and not writing reads "reading only" (she used to be told "denied"), writes on and reads off reads "writing only", and both keep the Open Settings link. The screen asks the read-side question only where `HealthPermissionProbe.readAccessDisclosed` is true, so on an iPhone it never asks it and the line is the write status alone, as before. **"Access past data" (issue #1549):** Health Connect hides everything older than 30 days before the app's first grant unless that switch (`READ_HEALTH_DATA_HISTORY`) is on, and a read made without it comes back short with no error. Two rules follow. An empty whole-history import says the store has nothing only when the switch was on for that read (`importPastDataGranted`, asked when a pass finishes; the screen keeps that answer with the result and does not re-read it on resume); otherwise it says older data is hidden and offers the way to Health Connect's settings. And the adapter remembers whether the whole-range read that minted its change token reached the older data (`reachedPastKey`, recorded on the first page of that read and only lowered afterwards: on its last page, and by any later pass that starts with the switch off); once the switch is on and it did not, the next pass drops the token and reads the whole range again (`HealthImportCursor.pastReadStep`, which is the whole rule and is unit tested). That re-read can run on a background pass. Without that, turning the switch on later imported nothing, ever: a changes-only pass does not return the older records, including ones another app wrote after the token was minted (seen on Android 15). The read/import disclosures live in `PRIVACY.md` §4/§10 and `docs/ops/play-health-declaration.md`; the Play Data safety and Health apps declarations still need a submission-time update (issue #21). **Open gap:** the server-side half of health-sync consent (a `profiles` column gating writes at the database layer) was described here as deferred to issue #188, but #188 is closed and no such column exists in production — tracked in issue #782. The clinical terminology mapping (`lib/domain/export/clinical_terminology.dart`, provenance record in `docs/clinical/`, issue #152) is **no longer dormant either**: the FHIR Bundle builder (#157) exists and consumes it (`lib/domain/export/fhir_bundle.dart` imports it directly).

- **Sharing model vocabulary (issue #3):** issue #3 asked for a "secure multi-user sharing and invitation system" and sketched a `profile_memberships` table with an `Owner / Co-Manager / Contributor / Viewer` role ladder. That design is already shipped, under different names, as issue #8's `public.profile_guardians` (`profile_memberships` -> `profile_guardians`) with roles `primary_guardian` (Owner), `co_parent` (Co-Manager), `caregiver` (Contributor), and `viewer` (Viewer) - see `lib/domain/models/profile_guardian.dart`'s `GuardianRole`. Re-deriving either under #3's names would be a rewrite of working, tested, security-reviewed code for no product gain; the gap-closure plan above maps #3's vocabulary onto the shipped schema rather than renaming it.

### Migration Flow

1. `npx supabase@2.116.0 migration new <name>` creates the file under `supabase/migrations/`; write imperative SQL and add or extend the pgTAP tests in `supabase/tests/`.
2. Run the suite locally: `npx supabase@2.116.0 start -x realtime,storage-api,imgproxy,mailpit,studio,edge-runtime,logflare,vector,supavisor`, then `db reset --local`, then `test db --local`.
3. Open a PR: the `db-tests` job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs the same suite.
4. Merge to `main`: [`.github/workflows/supabase-migrate.yml`](.github/workflows/supabase-migrate.yml) runs a separate `dry-run` job (issue #538: `db push --dry-run` plus a destructive-statement scan of every not-yet-applied migration via `.github/scripts/check-destructive-sql.sh`) gating a `migrate` job that runs `supabase link`, `db push`, then `supabase db query --linked "select public.reconcile_realtime_publication();"`, then deploys `feedback-notify`, `feedback-reply`, and `push-dispatch` (issue #163 added `push-dispatch` to this step — it had been live in production since issue #5 but was missing from the deploy step entirely until then), sets `push-dispatch`'s `FCM_*`/`PUSH_DISPATCH_WEBHOOK_SECRET` secrets (warning and skipping only that secret-set step, not the whole job, if those secrets aren't yet configured as `production` environment secrets — push-dispatch was already live with secrets set out-of-band), then (issue #17) checks the `delete-account` function's `APPLE_*` secrets and deploys it, reusing the project's existing values or warning and skipping only that secret-set step when the GitHub secrets are absent (issue #513 — no longer a hard failure) — all inside the `production` GitHub environment, waiting for the required reviewer. Only **after every one of those deploy steps** do two gates run, each gated only on a successful `supabase link` (`if: always() && steps.link.outcome == 'success'`, LLA-111): a **drift-detection gate** (`supabase db diff --linked --schema public --use-migra`, issue #163 — a non-empty diff is classified by `.github/scripts/classify-schema-diff.sh`, which warns on known function-re-emission/trigger-pair noise and fails on anything else, so a schema change made out-of-band, e.g. via Studio, or a migration that reached the project outside this workflow is caught immediately instead of going unnoticed) and a **database advisor gate** (`supabase db advisors --linked --type security`, issue #163, tightened by issue #454 — fails the job on any security-severity finding at warn level or above, aside from two narrowly documented exceptions; see item 5 below). Both gates run last, deliberately: they can only report on a deploy that already happened, never prevent it, so running them before the function deploys would let a false-positive finding block an unrelated function deploy instead of just flagging it afterward. The reconcile step is what makes the Realtime publication drift guard fire on every deploy (not just a from-scratch environment) — see the note on `20260905100000_realtime_publication.sql` above; it runs before the Apple-secret check so it is never skipped by a missing Apple key. Periodic reconciliation between deploys runs weekly via .github/workflows/supabase-reconcile.yml (Issue #453), so drift introduced between merges by a Studio toggle is caught without waiting for the next supabase/** push. A change to any Edge Function is proven first by `deno test` (every directory, `feedback-reply` included as of Issue #189, is in `deno.json`'s `test.include`); a branch touching a path `index.test.ts`'s fakes don't cover (e.g. `delete-account`'s real Apple-revoke calls) is also proven with local `supabase functions serve` + `curl` (`edge-runtime` must **not** be excluded from the `start` command for that - see `docs/ops/supabase-go-live.md`'s "delete-account Edge Function runbook").
5. **The advisor gate is CI-enforced, not manual (issue #163), and fails on `warn` or above since issue #454:** `supabase-migrate.yml`'s "Database advisor gate" step — the last step in the job — runs `supabase db advisors --linked --type security --level warn --output-format json` after every deploy (`--level warn` so the CLI itself omits INFO-level findings — production carries 7 by-design INFO-level `rls_enabled_no_policy` findings for service-only tables that this gate must never fail on), then pipes the result into `.github/scripts/check-advisor-gate.sh`, which also drops any INFO-level finding on its own as defense in depth (while still failing closed on a finding with no `level` field or an unrecognised level string) (unit tested: `.github/scripts/tests/check-advisor-gate.test.sh`; not the CLI's own `--fail-on`, which has no per-rule exclusion), which fails the job on any security-severity finding at warn level or above, with exactly two narrow, documented exceptions excluded by rule name — every other finding, including one this script has never seen before, still fails closed: `authenticated_security_definer_function_executable` (by design, covers roughly 30 RPCs — the whole point of that API is to be called by `authenticated`); `extension_in_public`, but only when it names `pg_net` specifically (issue #194's pg_net relocation is **deferred**, not done — production's pg_net is `supabase_admin`-owned and confirmed non-relocatable, and a plain migration risks either a permission failure that blocks every later migration or losing Supabase-managed grants on a recreate, so this needs a Supabase-supported path instead, tracked as a follow-up). A third exception, `auth_leaked_password_protection`, was removed on 2026-09-20 (issue #972) once the owner completed issue #18's dashboard checklist and turned leaked-password protection ON — the gate now fails on that finding like any other, so if it reappears the toggle was turned back off and issue #18 must be reopened rather than the exclusion re-added. The CLI has had a `db advisors` subcommand since at least the pinned 2.116.0 (confirmed via `supabase db --help`/`supabase db advisors --help`), so a human no longer needs to call the Supabase MCP `get_advisors` tool by hand before approving a run. The gate used to be pinned to `--fail-on error` because production carried tracked warn-level findings that would have failed every run: anon-executable `SECURITY DEFINER` functions (issue #158, since closed), `search_path` lints on four functions (issue #194 — two closed by the same PR that tightened this gate, two pre-existing functions outside its named scope left open), pg_net's extension-in-public lint (deferred, see above), and the dashboard-only leaked-password-protection setting (excluded at the time; issue #972 removed that exclusion on 2026-09-20 once the toggle was turned on, so the gate now fails on it). The MCP tool (against project `dleexnnevuuddcgcpztq`) remains useful for an ad hoc sweep outside a deploy, including `--type performance` findings, which the CI gate does not check (performance lints, e.g. an unindexed foreign key, are not a deploy blocker here).
6. **Touching `20260905100000_realtime_publication.sql` or the coordinator's subscription shape specifically:** also run `supabase/tests/manual/verify_realtime_delivery.mjs` (see its header for usage) against local Supabase started **without** excluding `realtime` (Docker required), or against the cloud project. This is a real websocket assertion of what Realtime actually delivers — pgTAP alone only proves catalog state (`db-tests` in CI runs with `-x realtime`, so it never exercises the real container). Not wired into CI (investigated and found out of proportion — see the plan's KTD4).
7. **Migration filenames must sort in the order they need to apply, not the order they were written:** `supabase db push` only applies migrations not yet recorded on the target project, in filename order, so a file that lands on `main` after another migration's timestamp but sorts *before* it would never actually run after it on a from-scratch environment. PR #105 review, item 3 (2026-09-06) found exactly this: this PR's three feedback migrations (`feedback_tickets`, `feedback_attachments_bucket`, `feedback_tickets_notified_at`) were all timestamped on 2026-09-05/06 mornings, before `20260906120000_account_deletion_final_rehome.sql` (merged to `main` via PR #106) existed on this branch — so after merging `main` in, they sorted *before* it despite needing to apply after it (`rehome_stray_day_entries` and the feedback schema touch disjoint tables, so there's no correctness dependency between them, but a stable, mergeable-in-any-order-you-review-them convention still needs *some* rule, and "sort after whatever is already on `main`" is it). Renamed to `20260906130000_feedback_tickets.sql`, `20260906140000_feedback_attachments_bucket.sql`, and `20260906150000_feedback_tickets_notified_at.sql` (each file's own header notes the rename and points back here) — the ordering discipline above (sort after whatever is already on `main`) holds regardless of by what path migrations actually reach the project. **Update (issue #163, 2026-09-08 — supersedes the "every run has failed" claim this paragraph used to make):** that claim, and issue #18's matching "the cloud project has no migrations and no public tables" account, were both stale. Verified live against `dleexnnevuuddcgcpztq` via the Supabase MCP (read-only queries — `list_migrations`, `list_tables`, `cron.job`, `list_edge_functions`) on 2026-09-08: **23 migrations applied** (including `20260906120000_account_deletion_final_rehome.sql` and `20260907010000_tags_element_length_check.sql`), **14 live tables with real rows**, **2 cron jobs active** (`lunarlog-nightly-caregiver-alerts`, `lunarlog-caregiver-alert-drain`), and **4 Edge Functions live** (`delete-account` v12, `feedback-notify` v10, `feedback-reply` v10, `push-dispatch` v4). So migrations have reached the project — whether entirely through `supabase-migrate.yml` once `SUPABASE_ACCESS_TOKEN` was provisioned, or partly by a manual push, is not fully reconstructable from the repo alone, and doesn't change the renaming guidance above either way. The gap issue #163 actually found is different and was real: `push-dispatch` and `20260907010000_tags_element_length_check.sql` had both reached production **without going through this workflow at all** — `push-dispatch` was missing from the Edge Function deploy step entirely, and nothing compared `supabase/migrations` against what the linked project had actually applied, so the workflow's own account of what it deploys had quietly drifted from what's live. Issue #163's drift-detection gate (`supabase db diff --linked --schema public`), the `push-dispatch` deploy addition, and the CI-enforced advisor gate (item 5 above) are what make `supabase-migrate.yml` a **CI-reproducible deploy path** again — one where "what's live" and "what this workflow deploys" can't silently diverge without failing a run.

8. **Constraint for #167/#172 (Issue #159 review finding, superseded by #167's actual shape below):** `sync_push` resolves every `day_entries`/`observations` row strictly by `id`, never by `(profile_id, source, source_id)` — so a `sync_push` payload alone cannot revive a tombstoned imported row the way a raw `insert ... on conflict (profile_id, source, source_id) where source_id is not null do update set deleted_at = null, ...` can (see `20260908170000_import_provenance.sql`'s header and `import_provenance_test.sql`'s tombstone-revive case). `bulk_import_entries(p_import_id, p_rows)` (`20260908190000_bulk_import.sql`) does not go through `sync_push` at all — it is exactly that raw set-based shape, run directly against `day_entries`, so dedup/revival happens for free via the `on conflict` arbiter with no local lookup step. The RPC's own dedup contract: every row must carry a non-null `source_id`, required at the RPC boundary (a null `source_id` is rejected, `'source_id is required for idempotent import'`) so a retry can never fall back to a bare insert that collides on `id` alone; a row whose `id` already exists in `day_entries` (any provenance) instead takes an update-by-id path with last-writer-wins on `updated_at`, mirroring `sync_push`'s own resolution, ahead of the `source_id` arbiter.

9. **Re-emitting `sync_push` (issue #181's derived allowlists):** the nine per-table key allowlists (`c_profile_keys`, `c_day_entry_keys`, `c_observation_keys`, `c_profile_mode_keys`, `c_cycle_override_keys`, `c_care_note_keys`, `c_visit_prep_item_keys`, `c_merge_event_keys`, `c_tag_registry_keys`) are embedded in the function body as `'{a,b,...}'` literals **derived from `public.sync_push_payload_keys(t)`** — never hand-restated. A migration that adds a synced column and re-emits `sync_push` must keep the derivation true: copy `20260917120000_sync_push_derived_allowlists.sql`'s DO-block pattern (template with `__SYNC_PUSH_*_KEYS__` placeholders, `replace()` with the derived literal, plus the migration-time assertions), carrying the then-current body verbatim as the template. `supabase/tests/sync_push_derived_allowlists_test.sql` re-derives from `information_schema` at test time and compares with the arrays embedded in the live function body (and asserts every `authenticated` write-granted column is covered), so a column added without re-deriving fails the suite — the `birth_year`/`relationship` bug class the derivation exists to close. Also regenerate `supabase/database.types.ts` (see the schema-snapshot bullet above) in the same change.

- **Issue triage — the `needs-agent-review` label:** an issue carrying
  `needs-agent-review` is waiting on an *agent* to do the analysis, not on the

  (`gh issue list --label needs-agent-review --state open`) and handle them
  before picking up ordinary backlog work: read the issue, verify its claims

  analysis is posted; add `needs-human-review` instead if what remains is a

- **Reusing the App Store Connect API key in a new iOS project:** `fastlane/Fastfile`'s `submit` lane is the real, working pattern — copy its shape rather than inventing a new one:
  ```ruby
  api_key = app_store_connect_api_key(
    key_id: ENV.fetch("ASC_KEY_ID"),
    issuer_id: ENV.fetch("ASC_ISSUER_ID"),
    key_content: ENV.fetch("ASC_PRIVATE_KEY"),
    in_house: false,
  )
  ```
  This `api_key` object is what every ASC-authenticated fastlane action takes (`deliver`, `pilot`, `latest_testflight_build_number`, `match`, `produce`, ...) — nothing else in a Fastfile needs a separate credential.
  - **Setting the three secrets on a new repo:** since `wjdavis5` is a personal GitHub account (not an Organization), there is no account-wide "org secret" — each repo needs its own copy of the same three values (2026-09-08 decision, tracked in this session). Read the key ID and issuer ID, and the `.p8` file itself, from the lab root `CLAUDE.md`'s Credential-locations table (`C:\git\CLAUDE.md`, outside this repo), then:
    ```bash
    gh secret set ASC_KEY_ID --repo <owner>/<new-repo> --body "CCKC22S4FN"
    gh secret set ASC_ISSUER_ID --repo <owner>/<new-repo> --body "<issuer id from the same table>"
    gh secret set ASC_PRIVATE_KEY --repo <owner>/<new-repo> < "C:\git\AuthKey_CCKC22S4FN.p8"
    ```
    Never echo the `.p8` contents or the issuer ID into chat, a commit, or any other file — read them directly from disk for the `gh secret set` call only.
  - **What this key does *not* cover:** it authenticates API calls; it does not manage certificates or provisioning profiles. This repo signs manually in CI (`ios/ExportOptions-ci.plist`, plain `xcodebuild`/`altool` in `ios-release.yml`) rather than via `fastlane match` — a new project needs its own signing setup (either the same manual pattern, mirroring `ios-release.yml`, or adopting `match`, which this account has not set up yet) and, separately, its own `IOS_DIST_CERT_P12_BASE64`/`IOS_DIST_CERT_PASSWORD`/`IOS_PROVISION_PROFILE_BASE64` secrets — the distribution cert can potentially be reused account-wide the same way the API key is, but the provisioning profile is tied to that project's own bundle ID and can never be copied from another app.
