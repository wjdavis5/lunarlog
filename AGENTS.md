# AGENTS.md — lunarlog

This document is the operating guide and technical context for AI agents working in this repository.

## Project Overview

`lunarlog` is a privacy-first family menstrual-cycle tracking application built with Flutter. It supports one adult operator managing multiple family profiles (including minors). The app is local-first (encrypted Drift/SQLCipher store behind a device-credential gate) with an optional Supabase account: email/password, native Google Sign-In (iOS and Android), native Apple Sign-In (iOS), or passwordless email (link or emailed code), offline-first sync of `profiles` and `day_entries` into RLS-protected Postgres via the `sync_push` RPC, in-app account deletion (server rows, the account, an Apple revocation when applicable, then the device reset - issue #17) and JSON export of a signed-in operator's own profiles and entries, and Sentry crash reporting behind an allowlist scrubber. An unconfigured build (no `--dart-define`s) has no account section, no sync, no crash reporting, and neither the export nor the delete tile.

Target platforms: iOS (iPhone first-class), Android, and web (iteration only; accounts and sync are off on web unless `LUNARLOG_WEB_SYNC=true`).

Implementation plans of record: [`docs/plans/2026-09-02-001-feat-supabase-auth-cloud-sync-plan.md`](docs/plans/2026-09-02-001-feat-supabase-auth-cloud-sync-plan.md) (accounts and sync), [`docs/plans/2026-09-03-001-feat-social-logins-plan.md`](docs/plans/2026-09-03-001-feat-social-logins-plan.md) (Google, passwordless email, identity linking; its IDs are cited with a `#2` prefix), [`docs/plans/2026-09-05-001-feat-account-deletion-and-json-export-plan.md`](docs/plans/2026-09-05-001-feat-account-deletion-and-json-export-plan.md) (in-app account deletion and JSON export, the App Store 5.1.1(v) release-gate clearer; its IDs are cited with a plain `#17` prefix), and [`docs/plans/2026-09-05-001-feat-in-app-feedback-support-plan.md`](docs/plans/2026-09-05-001-feat-in-app-feedback-support-plan.md) (in-app feedback/support, Issue #6). ### Database & Security Guidelines

### Migration Flow

1. `npx supabase@2.116.0 migration new <name>` creates the file under `supabase/migrations/`; write imperative SQL and add or extend the pgTAP tests in `supabase/tests/`.
2. Run the suite locally: `npx supabase@2.116.0 start -x realtime,storage-api,imgproxy,mailpit,studio,edge-runtime,logflare,vector,supavisor`, then `db reset --local`, then `test db --local`.
3. Open a PR: the `db-tests` job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs the same suite.
4. Merge to `main`: [`.github/workflows/supabase-migrate.yml`](.github/workflows/supabase-migrate.yml) runs `supabase link`, `db push --dry-run`, `db push`, and then `supabase db query --linked "select public.reconcile_realtime_publication();"` inside the `production` GitHub environment and waits for the required reviewer, then (issue #17) sets the `delete-account` function's `APPLE_*` secrets and deploys it. The reconcile step is what makes the Realtime publication drift guard fire on every deploy (not just a from-scratch environment) — see the note on `20260905100000_realtime_publication.sql` above; it runs before the Apple-secret check so it is never skipped by a missing Apple key. It is a **follow-up TODO**, not yet done, to also run this reconciliation *periodically* (e.g. a scheduled workflow) so drift introduced between merges by a Studio toggle is caught without waiting for the next `supabase/**` push. A change to a function outside `deno.json`'s `test.include` (`feedback-reply`, `delete-account`) is proven first with local `supabase functions serve` + `curl` (`edge-runtime` must **not** be excluded from the `start` command for that - see `docs/ops/supabase-go-live.md`'s "delete-account Edge Function runbook"), since neither has automated Deno coverage in CI yet.
5. **Before approving the run:** call the Supabase MCP `get_advisors` tool (security and performance lints; there is no CLI equivalent) against project `dleexnnevuuddcgcpztq` and confirm no security or RLS findings. The MCP server needs an interactive login (`authenticate` / `complete_authentication`) in the session that calls it.
6. **Touching `20260905100000_realtime_publication.sql` or the coordinator's subscription shape specifically:** also run `supabase/tests/manual/verify_realtime_delivery.mjs` (see its header for usage) against local Supabase started **without** excluding `realtime` (Docker required), or against the cloud project. This is a real websocket assertion of what Realtime actually delivers — pgTAP alone only proves catalog state (`db-tests` in CI runs with `-x realtime`, so it never exercises the real container). Not wired into CI (investigated and found out of proportion — see the plan's KTD4).
7. **Migration filenames must sort in the order they need to apply, not the order they were written:** `supabase db push` only applies migrations not yet recorded on the target project, in filename order, so a file that lands on `main` after another migration's timestamp but sorts *before* it would never actually run after it on a from-scratch environment. PR #105 review, item 3 (2026-09-06) found exactly this: this PR's three feedback migrations (`feedback_tickets`, `feedback_attachments_bucket`, `feedback_tickets_notified_at`) were all timestamped on 2026-09-05/06 mornings, before `20260906120000_account_deletion_final_rehome.sql` (merged to `main` via PR #106) existed on this branch — so after merging `main` in, they sorted *before* it despite needing to apply after it (`rehome_stray_day_entries` and the feedback schema touch disjoint tables, so there's no correctness dependency between them, but a stable, mergeable-in-any-order-you-review-them convention still needs *some* rule, and "sort after whatever is already on `main`" is it). Renamed to `20260906130000_feedback_tickets.sql`, `20260906140000_feedback_attachments_bucket.sql`, and `20260906150000_feedback_tickets_notified_at.sql` (each file's own header notes the rename and points back here) — safe to do because, per [`supabase-migrate.yml`](.github/workflows/supabase-migrate.yml)'s own run history (`gh run list --workflow=supabase-migrate.yml`), **every single run since this workflow's introduction has failed** at its "Check deploy credentials" step because the `production` environment's `SUPABASE_ACCESS_TOKEN` secret is unset (confirmed from the run logs, not inferred) — so no migration, including `20260906120000_account_deletion_final_rehome.sql` itself, has ever been successfully pushed to the linked remote project through CI. Whether someone has ever pushed manually (a local `supabase db push --linked` with a personal access token) is not something this could be verified from the repo alone — no CLI credentials were available in the environment this fix was made in (`supabase projects list` failed with `LegacyPlatformAuthRequiredError`, and `repos/lunarlog/.env` holds only `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_PROJECT_REF`, no access token). Renaming to sort after `main`'s current tip is the correct move either way: if nothing has ever been pushed, ordering among never-applied migrations is moot today but still needs to be right for whenever `SUPABASE_ACCESS_TOKEN` does get provisioned and the whole backlog pushes at once; if something *has* been pushed manually out-of-band, sorting after the tip is the only choice that isn't potentially wrong. **Fixing the actual `SUPABASE_ACCESS_TOKEN` gap is out of scope here and remains an open TODO** — someone with dashboard access needs to create a Supabase personal access token and add it as a `production` environment secret before `supabase-migrate.yml` can ever succeed.

## Config & Credential Locations

Credentials and environment variables live in:
- **App configuration (build-time dart-defines):** the app reads its client-side configuration from `lib/config.dart` (`AppConfig`) via `const String.fromEnvironment`. Keys:
  - `SUPABASE_URL` - project URL.

  - `SENTRY_DSN` - empty disables crash reporting.
  - `LUNARLOG_WEB_SYNC` - the literal `true` opts a web build into account sign-in and sync; never set in CI.
  - `GOOGLE_IOS_CLIENT_ID` / `GOOGLE_WEB_CLIENT_ID` - the Google OAuth client ids (`AppConfig.hasGoogle` needs both, non-web, and `hasSupabase`; empty hides the Google button). Client-safe, but held as GitHub repository secrets and in `dart_defines.json`, never committed as values. The iOS reversed client id (`com.googleusercontent.apps.<iOS client id>`) is a literal `CFBundleURLTypes` entry in `ios/Runner/Info.plist`, added in the same change that sets the ids; it is the one Google value that is committed.

Client-safe, but still defines so forks/PR builds compile with empty values and Manage guardians shows no Notifications tile.
  - Empty means unconfigured (`AppConfig.hasSupabase` / `hasSentry` are false); every workflow build must succeed with empty defines.
  - **Local run:** copy `dart_defines.example.json` to `dart_defines.json` (gitignored, client-safe values only) and run `flutter run --dart-define-from-file=dart_defines.json`.

## Development & Build Workflow

- **Worktree Isolation (Strict Requirement):** All new work, feature branches, PR reviews, and code changes MUST be performed in isolated git worktrees under `.worktrees/` (e.g. `.worktrees/pr-<n>` or `.worktrees/<branch-name>`). Never check out PR branches or make scratch changes in the primary checkout directory to avoid clobbering in-flight work.
- **Flutter SDK:** Flutter 3.47.2 stable / Dart 3.13.2.
- **Dependency Management:** `flutter pub get`
- **Linter:** `flutter analyze`
- **Tests:** `flutter test` and the pgTAP suite (see "Migration Flow").
- **Quality gates:** `dart run tool/quality_gate.dart` — 90% total line-coverage floor and a per-method CRAP gate (`comp² × (1 − cov/100)³ + comp`, gate at 10), both from one `flutter test --coverage` run filtered through `tool/quality/exclusions.dart`'s reviewed exclusion list (generated code plus platform adapters that can't run under `flutter test`); also the CI `check` job's step right after `flutter test`. `dart run tool/mutation_gate.dart` (`--full` for the whole `lib/`) is local-only mutation testing via the `mutation_test` package, scoped to changed files' test coverage when a direct test mirror exists; see README "Quality gates" for detail. `flutter test` alone is unaffected and stays the fast iteration loop.
- **Codegen:** after any Drift schema change, `dart run build_runner build --delete-conflicting-outputs` and commit `lib/data/db/db.g.dart`.
- **Android build note:** `flutter build apk` prints a Gradle warning that `sentry_flutter` 9.28.0 applies the Kotlin Gradle Plugin itself. It is upstream and harmless today; a future Flutter release may reject it, so re-check after every Flutter or `sentry_flutter` upgrade.
- **Device checklist:** auth links, Apple and Google Sign-In, magic links and emailed codes, adding or removing a sign-in method, two-device sync convergence, lock-mid-sync, the sign-out reset, account deletion (including the real Apple revocation), and JSON export cannot be covered by `flutter test`; they are verified by hand on iPhone and Android builds with a throwaway account per [`docs/ops/supabase-go-live.md`](docs/ops/supabase-go-live.md) ("Device checklist"). Use fabricated profiles only — never real family data.
- **Release gate:** in-app account deletion and JSON export shipped in code (issue #17), so App Store guideline 5.1.1(v)'s submission block (deletion required once account creation exists) is now closeable — but the gate itself is still mechanically closed: [`.github/scripts/check-release-gate.sh`](.github/scripts/check-release-gate.sh) fails closed unless the `RELEASE_GATE_ACCOUNT_DELETION` repository variable is set to `shipped`; a Play `production` dispatch additionally requires typing `production` into the `confirm_production` input. Flipping the variable — once issue #17 has merged and the device checklist above has passed — is a separate, deliberate release action, and so is `pubspec.yaml`'s `version:` bump and a `submit_for_review` dispatch of `ios-release.yml`. Pushes to `main` still upload to TestFlight and the Play `internal` track; that is acceptable for internal testing only.

  - Automated via [`.github/workflows/ios-release.yml`](.github/workflows/ios-release.yml) (mirrored from `taxiGame`).
