# AGENTS.md — lunarlog

This document is the operating guide and technical context for AI agents working in this repository.

## Project Overview

`lunarlog` is a privacy-first family menstrual-cycle tracking application built with Flutter, built around a Supabase account that syncs profiles across a household's devices and lets multiple guardians share a profile with distinct roles (`viewer`/`caregiver`/`co_parent`/`primary_guardian`) — sync and multi-guardian family collaboration are the product's priority and its differentiator, not an add-on. It supports one adult operator managing multiple family profiles (including minors). Local storage (a Drift/sqlite3 store behind a device-credential gate, relying on the OS's own at-rest protection rather than an app-managed cipher — see docs/ops/ios-export-compliance.md; schema v21 as of issue #597/#130 — v20 added `day_entries.pms_unconfirmed`/`profiles.units_unconfirmed` catch-up columns and a persisted `sync_state.cursor_deleted_profiles` pull cursor; v21 (issue #130) added the synced `day_entry_merge_events` table (same-date merge disclosures: one machine-written row per discarded `flow`/`note` value, retaining the losing text for author recovery, deduplicated by `(profile_id, losing_row_id, field)`, no tombstone — dismissal is device-local) with its `sync_state.cursor_day_entry_merge_events` pull cursor — see `lib/data/db/db.dart`'s schema-history doc comment for the full version-by-version list) keeps the app working when the network doesn't; that is a reliability property, not the product's identity. Sign-in methods: email/password, native Google Sign-In (iOS and Android), native Apple Sign-In (iOS), or passwordless email (link or emailed code). Offline-first sync of `profiles` and `day_entries` into RLS-protected Postgres runs via the `sync_push` RPC (which also carries, per issue #130, the `day_entry_merge_events` disclosure rows both resolvers emit — server-side inside the same-date resolver branch, client-side from `LunarLogStorage._resolveSameDateConflicts` through the same push path — with a 30-day server-side retention purge in `enforce_retention()`); other capabilities include in-app account deletion (server rows, the account, an Apple revocation when applicable, then the device reset - issue #17) and JSON export, available to any operator with a profile from Settings → Your data (no account required; server data is included only when signed in), and Sentry crash reporting behind an allowlist scrubber. An unconfigured build (no `--dart-define`s) has no account section, no sync, no crash reporting, and no delete tile (export remains available) — a development configuration for iterating without cloud credentials, not a supported product mode. See [`docs/product/positioning.md`](docs/product/positioning.md) for the full positioning rationale (audience, the family-collaboration story, and what lunarlog deliberately does not do). Settings → Your data also restores from the app's own export file (`lib/domain/import/account_import.dart`, `lib/data/import/account_importer.dart`; issue #140) via `file_picker` — same no-account-required scope, additive merge, nothing overwritten or deleted.

Target platforms: iOS (iPhone first-class), Android, and web (iteration only; accounts and sync are off on web unless `LUNARLOG_WEB_SYNC=true`).

Issue #243 refactored it to an injected-deps `handleDeleteAccount(req, deps)`/`buildDeps` shape (mirroring `feedback-notify`'s `handleFeedbackNotify`/`buildDeps` split) far enough to add `index.test.ts` coverage of its new fail-closed feedback-attachments Storage cleanup step below - not every branch (the Apple-revoke paths remain proven only by the curl runbook, not by `deno test`). It authenticates the caller from the `Authorization` header, fails closed with a distinct `400 apple_code_required` (nothing touched at all, #17 P1 round 2 fix) if the account has an Apple identity but no authorization code was supplied, then (Issue #243, D-24; reordered ahead of row deletion by the round 2 fix, 2026-09-08) lists and removes every object under the caller's `<uid>/` prefix in the `feedback-attachments` Storage bucket on a service-role client, paginating each `list()` call with `offset` until a page returns fewer entries than the requested limit and recursing into a nested folder entry to any depth (not just one level per ticket folder - the bucket's insert policy only constrains the first path segment), batching `remove()` at 100 paths per call - failing closed with its own `409 attachment_cleanup_failed` (mirroring `apple_revoke_failed`'s shape) on a listing or removal failure, before any row is touched, so the whole account stays untouched and retryable (`storage.objects.owner` is `on delete set null`, not a hard FK, so a deleted `auth.users` row cannot cascade-remove an orphaned attachment) - only then calls `delete_account_data()` on a user-scoped client (RLS holds), revokes the Apple identity via `_shared/apple_revoke.ts` whenever the account has one, failing closed with its own `409 apple_revoke_failed` (`auth.users` left in place, rows already gone) on a real revocation failure - never falling through to delete the user with revocation silently skipped - then persists the identity-bound `account_deletion_progress` marker (`apple_revoked_at`/`apple_identity_id`, Issue #527 tightened by Issue #605/LLA-051 so a retry after the account has since unlinked and relinked a different Apple identity never skips that new identity's own revoke) with one retry on a write failure and its own `409 apple_revocation_marker_failed` if both attempts fail (Issue #599 - previously best-effort, which could silently strand a retry needing a fresh code to re-revoke an already-revoked grant) - then runs a second, best-effort `rehome_stray_day_entries` pass on a service-role client with an explicit caller id (that function grants no `EXECUTE` to `authenticated` at all, #17 P1 round 2 fix), and finally deletes the `auth.users` row last on that same service-role client (KTD4 - the only irreversible step, so any attachment-cleanup or Apple failure leaves it in place and the whole call is retryable). The success log line also reports `attachmentsRemoved: <n>` (a count, never a path). `_shared/apple_revoke.ts` builds an ES256 client-secret JWT from the `APPLE_*` secrets (in-process via Deno's Web Crypto, never cached) to exchange a one-time Apple authorization code for a refresh token and revoke it immediately, with a 10s timeout on both Apple HTTP calls (a hung endpoint resolves to the same `network` failure as a dropped connection, KTD4); no Apple refresh token is ever stored (KTD3). `[functions.delete-account]` in `supabase/config.toml` sets `verify_jwt = true`. ### Migration Flow

1. `npx supabase@2.116.0 migration new <name>` creates the file under `supabase/migrations/`; write imperative SQL and add or extend the pgTAP tests in `supabase/tests/`.
2. Run the suite locally: `npx supabase@2.116.0 start -x realtime,storage-api,imgproxy,mailpit,studio,edge-runtime,logflare,vector,supavisor`, then `db reset --local`, then `test db --local`.
3. Open a PR: the `db-tests` job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs the same suite.
4. Merge to `main`: [`.github/workflows/supabase-migrate.yml`](.github/workflows/supabase-migrate.yml) runs `supabase link`, `db push --dry-run`, `db push`, then `supabase db query --linked "select public.reconcile_realtime_publication();"`, then deploys `feedback-notify`, `feedback-reply`, and `push-dispatch` (issue #163 added `push-dispatch` to this step — it had been live in production since issue #5 but was missing from the deploy step entirely until then), sets `push-dispatch`'s `FCM_*`/`PUSH_DISPATCH_WEBHOOK_SECRET` secrets (warning and skipping only that secret-set step, not the whole job, if those secrets aren't yet configured as `production` environment secrets — push-dispatch was already live with secrets set out-of-band), then (issue #17) sets the `delete-account` function's `APPLE_*` secrets (hard-failing just its own secret-set/deploy steps if missing) and deploys it — all inside the `production` GitHub environment, waiting for the required reviewer. Only **after every one of those deploy steps** does it run a **drift-detection gate** (`supabase db diff --linked --schema public`, issue #163 — fails the job on any non-empty diff, so a schema change made out-of-band, e.g. via Studio, or a migration that reached the project outside this workflow is caught immediately instead of going unnoticed) and a **database advisor gate** (`supabase db advisors --linked --type security`, issue #163, tightened by issue #454 — fails the job on any security-severity finding at warn level or above, aside from three narrowly documented exceptions; see item 5 below). Both gates run last, deliberately: they can only report on a deploy that already happened, never prevent it, so running them before the function deploys would let a false-positive finding block an unrelated function deploy instead of just flagging it afterward. The reconcile step is what makes the Realtime publication drift guard fire on every deploy (not just a from-scratch environment) — see the note on `20260905100000_realtime_publication.sql` above; it runs before the Apple-secret check so it is never skipped by a missing Apple key. Periodic reconciliation between deploys runs weekly via .github/workflows/supabase-reconcile.yml (Issue #453), so drift introduced between merges by a Studio toggle is caught without waiting for the next supabase/** push. A change to any Edge Function is proven first by `deno test` (every directory, `feedback-reply` included as of Issue #189, is in `deno.json`'s `test.include`); a branch touching a path `index.test.ts`'s fakes don't cover (e.g. `delete-account`'s real Apple-revoke calls) is also proven with local `supabase functions serve` + `curl` (`edge-runtime` must **not** be excluded from the `start` command for that - see `docs/ops/supabase-go-live.md`'s "delete-account Edge Function runbook").
5. **The advisor gate is CI-enforced, not manual (issue #163), and fails on `warn` or above since issue #454:** `supabase-migrate.yml`'s "Database advisor gate" step — the last step in the job — runs `supabase db advisors --linked --type security --level warn --output-format json` after every deploy (`--level warn` so the CLI itself omits INFO-level findings — production carries 7 by-design INFO-level `rls_enabled_no_policy` findings for service-only tables that this gate must never fail on), then pipes the result into `.github/scripts/check-advisor-gate.sh`, which also drops any INFO-level finding on its own as defense in depth (while still failing closed on a finding with no `level` field or an unrecognised level string) (unit tested: `.github/scripts/tests/check-advisor-gate.test.sh`; not the CLI's own `--fail-on`, which has no per-rule exclusion), which fails the job on any security-severity finding at warn level or above, with exactly three narrow, documented exceptions excluded by rule name — every other finding, including one this script has never seen before, still fails closed: `authenticated_security_definer_function_executable` (by design, covers roughly 30 RPCs — the whole point of that API is to be called by `authenticated`); `extension_in_public`, but only when it names `pg_net` specifically (issue #194's pg_net relocation is **deferred**, not done — production's pg_net is `supabase_admin`-owned and confirmed non-relocatable, and a plain migration risks either a permission failure that blocks every later migration or losing Supabase-managed grants on a recreate, so this needs a Supabase-supported path instead, tracked as a follow-up); and `auth_leaked_password_protection` (a dashboard-only Auth toggle, confirmed OFF in production, already on the owner's manual post-deploy checklist from issue #694 — remove this exclusion once that checklist item is done). The CLI has had a `db advisors` subcommand since at least the pinned 2.116.0 (confirmed via `supabase db --help`/`supabase db advisors --help`), so a human no longer needs to call the Supabase MCP `get_advisors` tool by hand before approving a run. 7. **Migration filenames must sort in the order they need to apply, not the order they were written:** `supabase db push` only applies migrations not yet recorded on the target project, in filename order, so a file that lands on `main` after another migration's timestamp but sorts *before* it would never actually run after it on a from-scratch environment. PR #105 review, item 3 (2026-09-06) found exactly this: this PR's three feedback migrations (`feedback_tickets`, `feedback_attachments_bucket`, `feedback_tickets_notified_at`) were all timestamped on 2026-09-05/06 mornings, before `20260906120000_account_deletion_final_rehome.sql` (merged to `main` via PR #106) existed on this branch — so after merging `main` in, they sorted *before* it despite needing to apply after it (`rehome_stray_day_entries` and the feedback schema touch disjoint tables, so there's no correctness dependency between them, but a stable, mergeable-in-any-order-you-review-them convention still needs *some* rule, and "sort after whatever is already on `main`" is it). 8. **Constraint for #167/#172 (Issue #159 review finding, superseded by #167's actual shape below):** `sync_push` resolves every `day_entries`/`observations` row strictly by `id`, never by `(profile_id, source, source_id)` — so a `sync_push` payload alone cannot revive a tombstoned imported row the way a raw `insert ... on conflict (profile_id, source, source_id) where source_id is not null do update set deleted_at = null, ...` can (see `20260908170000_import_provenance.sql`'s header and `import_provenance_test.sql`'s tombstone-revive case). `bulk_import_entries(p_import_id, p_rows)` (`20260908190000_bulk_import.sql`) does not go through `sync_push` at all — it is exactly that raw set-based shape, run directly against `day_entries`, so dedup/revival happens for free via the `on conflict` arbiter with no local lookup step. The RPC's own dedup contract: every row must carry a non-null `source_id`, required at the RPC boundary (a null `source_id` is rejected, `'source_id is required for idempotent import'`) so a retry can never fall back to a bare insert that collides on `id` alone; a row whose `id` already exists in `day_entries` (any provenance) instead takes an update-by-id path with last-writer-wins on `updated_at`, mirroring `sync_push`'s own resolution, ahead of the `source_id` arbiter.

9. **Re-emitting `sync_push` (issue #181's derived allowlists):** the nine per-table key allowlists (`c_profile_keys`, `c_day_entry_keys`, `c_observation_keys`, `c_profile_mode_keys`, `c_cycle_override_keys`, `c_care_note_keys`, `c_visit_prep_item_keys`, `c_merge_event_keys`, `c_tag_registry_keys`) are embedded in the function body as `'{a,b,...}'` literals **derived from `public.sync_push_payload_keys(t)`** — never hand-restated. A migration that adds a synced column and re-emits `sync_push` must keep the derivation true: copy `20260917120000_sync_push_derived_allowlists.sql`'s DO-block pattern (template with `__SYNC_PUSH_*_KEYS__` placeholders, `replace()` with the derived literal, plus the migration-time assertions), carrying the then-current body verbatim as the template. `supabase/tests/sync_push_derived_allowlists_test.sql` re-derives from `information_schema` at test time and compares with the arrays embedded in the live function body (and asserts every `authenticated` write-granted column is covered), so a column added without re-deriving fails the suite — the `birth_year`/`relationship` bug class the derivation exists to close. Also regenerate `supabase/database.types.ts` (see the schema-snapshot bullet above) in the same change.

10. **Pre-push migration safety (issue #185): undo notes for row-rewriting migrations, plus the workflow's PITR gate and dry-run assertion.** Any migration that REWRITES stored rows — an `UPDATE`/`DELETE`/backfill over existing data, not pure DDL — must carry a header comment block starting `UNDO:` describing the recovery statement. The block must be *truthful*: if a real SQL inverse exists (a `create or replace` whose previous body can simply be re-emitted forward, a constraint that can be re-dropped), write it; if none exists, say so and write what recovery actually means — for the row-rewrite class that is a PITR restore of the project to a pre-migration recovery point, a *whole-project* rewind that also loses every write made after the migration ran, which is exactly the cost the author must confront before merge rather than after an incident. The precedent retrofit is `supabase/migrations/20260907010000_tags_element_length_check.sql` (#94's pre-clean): its `UNDO:` block states there is no SQL inverse (the dropped over-length elements are staged nowhere) and that the schema-only steps being individually invertible does nothing for already-cleaned rows. A comment-only edit to an already-applied migration is safe — a migration file's identity to `supabase db push` is its *filename* (the `schema_migrations` version key), and comments never reach the database — which is how that retrofit (and any future UNDO-note addition) ships without re-running anything; it does not relax the "never edit a merged migration's SQL in place" rule, which stays absolute. Two `supabase-migrate.yml` gates back this convention up: the migrate job's **PITR gate** ([`.github/scripts/check-pitr-gate.sh`](.github/scripts/check-pitr-gate.sh)) fails closed before `db push` unless the `SUPABASE_PITR_CONFIRMED` repository variable is `true` — a **one-time operator action** (verify backups/PITR on the Supabase dashboard, Project Settings → Database → Backups, per the checklist in [`docs/ops/supabase-go-live.md`](docs/ops/supabase-go-live.md) and issue #18, then set the variable by hand — never from automation, a coordinator, or a PR); and the dry-run job's **dry-run list assertion** ([`.github/scripts/assert-pending-migrations.sh`](.github/scripts/assert-pending-migrations.sh)) fails the run when the migrations `db push --dry-run` would apply are not exactly the migration files the push *added* (`git diff --diff-filter=A before..HEAD -- supabase/migrations`) — "extra" means production is behind the repo (an earlier deploy failed or was reverted), "missing" means a pushed migration already exists out-of-band. Both scripts' truth tables run in CI's `release-guards` job.

Old dumps (`drift_schema_v1.json` … `v<N-1>.json`) are never touched again; if a version was ever reconstructed from git history rather than dumped live (see that test file's doc comment for how v1–v3 were rebuilt from commits `f4923a4`/`dda8e74`/`f1ea1e2` when this harness was first built), it stays exactly as dumped.
    3. `dart run drift_dev schema generate drift_schemas/ test/data/db/generated_migrations/` — regenerates **every** `schema_v*.dart` file and `schema.dart`'s `GeneratedHelper`, not just the new version's.
    4. Add `<N - 1>` to `schema_migration_test.dart`'s `_kOlderSchemaVersions` list and bump `_kCurrentSchemaVersion` to `N`.
    5. No `.github/workflows/ci.yml` edit needed here (issue #576): its "Codegen freshness" step derives the `drift_dev schema dump` output filename from `db.dart`'s `schemaVersion` getter at run time (`drift_schema_v<version>.json`), so bumping `schemaVersion` above is enough — CI dumps into the new file on its own and fails on a dirty tree exactly as it does for `db.g.dart`.

- **Reusing the App Store Connect API key in a new iOS project:** `fastlane/Fastfile`'s `submit` lane is the real, working pattern — copy its shape rather than inventing a new one:
  ```ruby
  api_key = app_store_connect_api_key(
    key_id: ENV.fetch("ASC_KEY_ID"),
    issuer_id: ENV.fetch("ASC_ISSUER_ID"),
    key_content: ENV.fetch("ASC_PRIVATE_KEY"),
    in_house: false,
  )
  ```
  This `api_key` object is what every ASC-authenticated fastlane action takes (`deliver`, `pilot`, `latest_testflight_build_number`, `match`, `produce`, ...) — nothing else in a Fastfile needs a separate credential.
  - **Setting the three secrets on a new repo:** since `wjdavis5` is a personal GitHub account (not an Organization), there is no account-wide "org secret" — each repo needs its own copy of the same three values (2026-09-08 decision, tracked in this session). Read the key ID and issuer ID, and the `.p8` file itself, from the lab root `CLAUDE.md`'s Credential-locations table (`C:\git\CLAUDE.md`, outside this repo), then:
    ```bash
    gh secret set ASC_KEY_ID --repo <owner>/<new-repo> --body "CCKC22S4FN"
    gh secret set ASC_ISSUER_ID --repo <owner>/<new-repo> --body "<issuer id from the same table>"
    gh secret set ASC_PRIVATE_KEY --repo <owner>/<new-repo> < "C:\git\AuthKey_CCKC22S4FN.p8"
    ```
    Never echo the `.p8` contents or the issuer ID into chat, a commit, or any other file — read them directly from disk for the `gh secret set` call only.
  - **What this key does *not* cover:** it authenticates API calls; it does not manage certificates or provisioning profiles. This repo signs manually in CI (`ios/ExportOptions-ci.plist`, plain `xcodebuild`/`altool` in `ios-release.yml`) rather than via `fastlane match` — a new project needs its own signing setup (either the same manual pattern, mirroring `ios-release.yml`, or adopting `match`, which this account has not set up yet) and, separately, its own `IOS_DIST_CERT_P12_BASE64`/`IOS_DIST_CERT_PASSWORD`/`IOS_PROVISION_PROFILE_BASE64` secrets — the distribution cert can potentially be reused account-wide the same way the API key is, but the provisioning profile is tied to that project's own bundle ID and can never be copied from another app.
