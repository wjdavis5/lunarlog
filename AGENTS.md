# AGENTS.md — lunarlog

This document is the operating guide and technical context for AI agents working in this repository.

## Project Overview

`lunarlog` is a privacy-first family menstrual-cycle tracking application built with Flutter, built around a Supabase account that syncs profiles across a household's devices and lets multiple guardians share a profile with distinct roles (`viewer`/`caregiver`/`co_parent`/`primary_guardian`) — sync and multi-guardian family collaboration are the product's priority and its differentiator, not an add-on. It supports one adult operator managing multiple family profiles (including minors). Local storage (a Drift/sqlite3 store behind a device-credential gate, relying on the OS's own at-rest protection rather than an app-managed cipher — see docs/ops/ios-export-compliance.md) keeps the app working when the network doesn't; that is a reliability property, not the product's identity. Sign-in methods: email/password, native Google Sign-In (iOS and Android), native Apple Sign-In (iOS), or passwordless email (link or emailed code). Offline-first sync of `profiles` and `day_entries` into RLS-protected Postgres runs via the `sync_push` RPC; other capabilities include in-app account deletion (server rows, the account, an Apple revocation when applicable, then the device reset - issue #17) and JSON export, available to any operator with a profile from Settings → Your data (no account required; server data is included only when signed in), and Sentry crash reporting behind an allowlist scrubber. An unconfigured build (no `--dart-define`s) has no account section, no sync, no crash reporting, and no delete tile (export remains available) — a development configuration for iterating without cloud credentials, not a supported product mode. See [`docs/product/positioning.md`](docs/product/positioning.md) for the full positioning rationale (audience, the family-collaboration story, and what lunarlog deliberately does not do). Settings → Your data also restores from the app's own export file (`lib/domain/import/account_import.dart`, `lib/data/import/account_importer.dart`; issue #140) via `file_picker` — same no-account-required scope, additive merge, nothing overwritten or deleted.

Target platforms: iOS (iPhone first-class), Android, and web (iteration only; accounts and sync are off on web unless `LUNARLOG_WEB_SYNC=true`).

### Migration Flow

1. `npx supabase@2.116.0 migration new <name>` creates the file under `supabase/migrations/`; write imperative SQL and add or extend the pgTAP tests in `supabase/tests/`.
2. Run the suite locally: `npx supabase@2.116.0 start -x realtime,storage-api,imgproxy,mailpit,studio,edge-runtime,logflare,vector,supavisor`, then `db reset --local`, then `test db --local`.
3. Open a PR: the `db-tests` job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs the same suite.
4. Merge to `main`: [`.github/workflows/supabase-migrate.yml`](.github/workflows/supabase-migrate.yml) runs `supabase link`, `db push --dry-run`, `db push`, then `supabase db query --linked "select public.reconcile_realtime_publication();"`, then deploys `feedback-notify`, `feedback-reply`, and `push-dispatch` (issue #163 added `push-dispatch` to this step — it had been live in production since issue #5 but was missing from the deploy step entirely until then), sets `push-dispatch`'s `FCM_*`/`PUSH_DISPATCH_WEBHOOK_SECRET` secrets (warning and skipping only that secret-set step, not the whole job, if those secrets aren't yet configured as `production` environment secrets — push-dispatch was already live with secrets set out-of-band), then (issue #17) sets the `delete-account` function's `APPLE_*` secrets (hard-failing just its own secret-set/deploy steps if missing) and deploys it — all inside the `production` GitHub environment, waiting for the required reviewer. Only **after every one of those deploy steps** does it run a **drift-detection gate** (`supabase db diff --linked --schema public`, issue #163 — fails the job on any non-empty diff, so a schema change made out-of-band, e.g. via Studio, or a migration that reached the project outside this workflow is caught immediately instead of going unnoticed) and a **database advisor gate** (`supabase db advisors --linked --type security --fail-on error`, issue #163 — fails the job on any security-severity finding at error level). Both gates run last, deliberately: they can only report on a deploy that already happened, never prevent it, so running them before the function deploys would let a false-positive finding block an unrelated function deploy instead of just flagging it afterward. The reconcile step is what makes the Realtime publication drift guard fire on every deploy (not just a from-scratch environment) — see the note on `20260905100000_realtime_publication.sql` above; it runs before the Apple-secret check so it is never skipped by a missing Apple key. It is a **follow-up TODO**, not yet done, to also run this reconciliation *periodically* (e.g. a scheduled workflow) so drift introduced between merges by a Studio toggle is caught without waiting for the next `supabase/**` push. A change to `feedback-reply`, the one function still outside `deno.json`'s `test.include`, is proven first with local `supabase functions serve` + `curl` (`edge-runtime` must **not** be excluded from the `start` command for that - see `docs/ops/supabase-go-live.md`'s "delete-account Edge Function runbook", which still applies to any `delete-account` branch `index.test.ts`'s fakes don't cover, e.g. the Apple-revoke paths), since it has no automated Deno coverage in CI.
5. **The advisor gate is CI-enforced, not manual (issue #163), and currently fails only on `error`:** `supabase-migrate.yml`'s "Database advisor gate" step — the last step in the job — runs `supabase db advisors --linked --type security --fail-on error` after every deploy and fails the job on any security-severity finding at error level — the CLI has had a `db advisors` subcommand since at least the pinned 2.116.0 (confirmed via `supabase db --help`/`supabase db advisors --help`), so a human no longer needs to call the Supabase MCP `get_advisors` tool by hand before approving a run. It is pinned to `--fail-on error` rather than `warn` because production currently carries tracked warn-level findings that would fail every run until they land: anon-executable `SECURITY DEFINER` functions (issue #158, in flight), `search_path` and extension-in-public lints (issue #194), and the dashboard-only leaked-password-protection setting. **TODO(#163 follow-up):** tighten to `--fail-on warn` once #158, #194, and leaked-password protection are done. The MCP tool (against project `dleexnnevuuddcgcpztq`) remains useful for an ad hoc sweep outside a deploy, including `--type performance` findings, which the CI gate does not check (performance lints, e.g. an unindexed foreign key, are not a deploy blocker here).
6. **Touching `20260905100000_realtime_publication.sql` or the coordinator's subscription shape specifically:** also run `supabase/tests/manual/verify_realtime_delivery.mjs` (see its header for usage) against local Supabase started **without** excluding `realtime` (Docker required), or against the cloud project. This is a real websocket assertion of what Realtime actually delivers — pgTAP alone only proves catalog state (`db-tests` in CI runs with `-x realtime`, so it never exercises the real container). Not wired into CI (investigated and found out of proportion — see the plan's KTD4).
7. **Migration filenames must sort in the order they need to apply, not the order they were written:** `supabase db push` only applies migrations not yet recorded on the target project, in filename order, so a file that lands on `main` after another migration's timestamp but sorts *before* it would never actually run after it on a from-scratch environment. PR #105 review, item 3 (2026-09-06) found exactly this: this PR's three feedback migrations (`feedback_tickets`, `feedback_attachments_bucket`, `feedback_tickets_notified_at`) were all timestamped on 2026-09-05/06 mornings, before `20260906120000_account_deletion_final_rehome.sql` (merged to `main` via PR #106) existed on this branch — so after merging `main` in, they sorted *before* it despite needing to apply after it (`rehome_stray_day_entries` and the feedback schema touch disjoint tables, so there's no correctness dependency between them, but a stable, mergeable-in-any-order-you-review-them convention still needs *some* rule, and "sort after whatever is already on `main`" is it). Renamed to `20260906130000_feedback_tickets.sql`, `20260906140000_feedback_attachments_bucket.sql`, and `20260906150000_feedback_tickets_notified_at.sql` (each file's own header notes the rename and points back here) — the ordering discipline above (sort after whatever is already on `main`) holds regardless of by what path migrations actually reach the project. **Update (issue #163, 2026-09-08 — supersedes the "every run has failed" claim this paragraph used to make):** that claim, and issue #18's matching "the cloud project has no migrations and no public tables" account, were both stale. Verified live against `dleexnnevuuddcgcpztq` via the Supabase MCP (read-only queries — `list_migrations`, `list_tables`, `cron.job`, `list_edge_functions`) on 2026-09-08: **23 migrations applied** (including `20260906120000_account_deletion_final_rehome.sql` and `20260907010000_tags_element_length_check.sql`), **14 live tables with real rows**, **2 cron jobs active** (`lunarlog-nightly-caregiver-alerts`, `lunarlog-caregiver-alert-drain`), and **4 Edge Functions live** (`delete-account` v12, `feedback-notify` v10, `feedback-reply` v10, `push-dispatch` v4). So migrations have reached the project — whether entirely through `supabase-migrate.yml` once `SUPABASE_ACCESS_TOKEN` was provisioned, or partly by a manual push, is not fully reconstructable from the repo alone, and doesn't change the renaming guidance above either way. The gap issue #163 actually found is different and was real: `push-dispatch` and `20260907010000_tags_element_length_check.sql` had both reached production **without going through this workflow at all** — `push-dispatch` was missing from the Edge Function deploy step entirely, and nothing compared `supabase/migrations` against what the linked project had actually applied, so the workflow's own account of what it deploys had quietly drifted from what's live. Issue #163's drift-detection gate (`supabase db diff --linked --schema public`), the `push-dispatch` deploy addition, and the CI-enforced advisor gate (item 5 above) are what make `supabase-migrate.yml` a **CI-reproducible deploy path** again — one where "what's live" and "what this workflow deploys" can't silently diverge without failing a run.

8. **Constraint for #167/#172 (Issue #159 review finding, superseded by #167's actual shape below):** `sync_push` resolves every `day_entries`/`observations` row strictly by `id`, never by `(profile_id, source, source_id)` — so a `sync_push` payload alone cannot revive a tombstoned imported row the way a raw `insert ... on conflict (profile_id, source, source_id) where source_id is not null do update set deleted_at = null, ...` can (see `20260908170000_import_provenance.sql`'s header and `import_provenance_test.sql`'s tombstone-revive case). `bulk_import_entries(p_import_id, p_rows)` (`20260908190000_bulk_import.sql`) does not go through `sync_push` at all — it is exactly that raw set-based shape, run directly against `day_entries`, so dedup/revival happens for free via the `on conflict` arbiter with no local lookup step. The RPC's own dedup contract: every row must carry a non-null `source_id`, required at the RPC boundary (a null `source_id` is rejected, `'source_id is required for idempotent import'`) so a retry can never fall back to a bare insert that collides on `id` alone; a row whose `id` already exists in `day_entries` (any provenance) instead takes an update-by-id path with last-writer-wins on `updated_at`, mirroring `sync_push`'s own resolution, ahead of the `source_id` arbiter.

## Development & Build Workflow

- **Worktree Isolation (Strict Requirement):** All new work, feature branches, PR reviews, and code changes MUST be performed in isolated git worktrees under `.worktrees/` (e.g. `.worktrees/pr-<n>` or `.worktrees/<branch-name>`). Never check out PR branches or make scratch changes in the primary checkout directory to avoid clobbering in-flight work.
- **Flutter SDK:** Flutter 3.47.2 stable / Dart 3.13.2.
- **Dependency Management:** `flutter pub get`
- **Linter:** `flutter analyze`
- **Tests:** `flutter test` and the pgTAP suite (see "Migration Flow").
- **Quality gates:** `dart run tool/quality_gate.dart` — 90% total line-coverage floor and a per-method CRAP gate (`comp² × (1 − cov/100)³ + comp`, gate at 10), both from one `flutter test --coverage` run filtered through `tool/quality/exclusions.dart`'s reviewed exclusion list (generated code plus platform adapters that can't run under `flutter test`); also the CI `check` job's step right after `flutter test`. `dart run tool/mutation_gate.dart` (`--full` for the whole `lib/`) is local-only mutation testing via the `mutation_test` package, scoped to changed files' test coverage when a direct test mirror exists; see README "Quality gates" for detail. `flutter test` alone is unaffected and stays the fast iteration loop.
- **Codegen:** after any Drift schema change, `dart run build_runner build --delete-conflicting-outputs` and commit `lib/data/db/db.g.dart`. The `check` job in `.github/workflows/ci.yml` re-runs this (plus the schema dump below) and fails the build on a dirty tree, so a forgotten regeneration is caught in CI even if missed locally.
  - **Bumping `schemaVersion` (issue #200 — drift schema-verification harness):** the harness in `test/data/db/schema_migration_test.dart` proves every historical `onUpgradeSteps` path lands on a schema identical to the current one, using dumps committed under `drift_schemas/` and the generated helpers under `test/data/db/generated_migrations/` (both drift_dev output — the latter is excluded from the coverage/CRAP gates in `tool/quality/exclusions.dart`, same treatment as `*.g.dart`). After adding the new `if (from < N)` block to `onUpgradeSteps` and bumping `schemaVersion`:
    1. `dart run build_runner build --delete-conflicting-outputs` (as above).
    2. `dart run drift_dev schema dump lib/data/db/db.dart drift_schemas/drift_schema_v<N>.json` — dumps the **new current** version. Old dumps (`drift_schema_v1.json` … `v<N-1>.json`) are never touched again; if a version was ever reconstructed from git history rather than dumped live (see that test file's doc comment for how v1–v3 were rebuilt from commits `f4923a4`/`dda8e74`/`f1ea1e2` when this harness was first built), it stays exactly as dumped.
    3. `dart run drift_dev schema generate drift_schemas/ test/data/db/generated_migrations/` — regenerates **every** `schema_v*.dart` file and `schema.dart`'s `GeneratedHelper`, not just the new version's.
    4. Add `<N - 1>` to `schema_migration_test.dart`'s `_kOlderSchemaVersions` list and bump `_kCurrentSchemaVersion` to `N`.
    5. Update `.github/workflows/ci.yml`'s "Codegen freshness" step: its `drift_dev schema dump` command's output filename is hardcoded to the current version and must be bumped to `drift_schema_v<N>.json` too, or CI will dump into the old file and the (now-stale) new dump will never get generated in CI, silently passing on a real drift.
    6. `flutter test test/data/db/schema_migration_test.dart` before the full suite — a mismatch here means either `onUpgradeSteps` doesn't fully reach the new schema, or a raw `customStatement`-created object (like `kLiveDayEntryIndexSql`'s partial index) needs its own explicit assertion the way that file already has one, since `SchemaVerifier.migrateAndValidate`'s structural comparison cannot see anything outside the drift table/column/index DSL.
