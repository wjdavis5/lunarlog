## Residual Review Findings

- **P3** — `.github/workflows/play-store-release.yml:242` — The Android native-symbol upload path is hardcoded to one AGP-version-specific intermediates path and silently degrades to a `::warning::` (not a failure) if that path doesn't exist on a future AGP/Flutter upgrade. This is the plan's own KTD10 posture applied consistently ("a telemetry secret/path issue must never block a release"), not an oversight — but it does mean a future AGP layout change would silently stop native-symbol upload with only a workflow-log warning as the signal. Follow-up: if this is ever missed, check whether the `mergeReleaseNativeLibs` path segment (already discovered empirically once, see the `fix(release): correct the Android native-libs path` commit) has moved again.
- **P3** — `.github/workflows/play-store-release.yml:249` — The ProGuard mapping upload (`sentry-cli upload-proguard`) has no accompanying build-time UUID embedding (normally via the Sentry Gradle plugin or `sentry-debug-meta.properties`), so even once R8/minification is enabled, uploaded mappings may not match the UUID a crash event carries, leaving stack traces obfuscated despite an apparently successful upload. Out of scope for this plan (R8 is explicitly deferred — see the plan's Scope Boundaries and `docs/ops/supabase-go-live.md`'s note that the ProGuard upload is "a no-op until R8/minification is separately enabled"); flag this UUID-matching gap when R8 is actually enabled in a future issue.
- **P4** — `.github/workflows/ios-release.yml` / `play-store-release.yml` — The two Sentry symbol-upload steps still duplicate their `env:` block shape and the `bash upload-sentry-symbols-setup.sh` + `if [ -x ./sentry-cli ]` invocation pattern (the guard/download/checksum-verify logic itself was already deduped into the shared script during the simplify pass). A composite GitHub Action taking the download URL/checksum/tool and upload command(s) as inputs would collapse this further, but this repo has no existing composite-action convention (`.github/actions/` doesn't exist) — introducing one would be a first-of-its-kind structural change, not a drop-in fix. Not worth the risk for this plan; revisit if a third release workflow needs the same pattern.
- **P4** — `.github/workflows/play-store-release.yml:244` — The native-libs upload and the ProGuard mapping upload run sequentially even though they're independent Sentry API calls; backgrounding them (`&` + `wait`) would shave a little wall time off each Play Store release. Low value relative to the added error-handling complexity of two potentially-failing background jobs in a release script.
- **P4** — `lib/observability/route_names.dart` — Whether a newly pushed screen or modal route gets a `RouteSettings` name (and a matching `kSentryRouteNames` entry) is enforced only by doc-comment convention and the existing tests' "every name actually observed is registered" checks — there's no static/lint enforcement that *every* navigable destination is named, so a future screen added without a registry entry fails silently (reports `unknown` forever, no test failure, no CI signal). This is the plan's own accepted risk, documented in its Risk table ("registry membership is the real defense... the load-bearing guard is U2's test asserting every name a push site emits is in `kSentryRouteNames`") — a static-analysis-based enforcement would be a real feature addition, out of scope here.
