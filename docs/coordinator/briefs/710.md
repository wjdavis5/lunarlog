# Brief — #710 ops(qa): seed the Apple test account with rich, realistic sample data

Facts below verified against `origin/main` @ `1cffef68` by an explore agent on 2026-09-14.

## What to build

An operator-run, never-shipped-in-the-app **Dart CLI** at `tool/seed_test_accounts/` (entry: `dart run tool/seed_test_accounts/main.dart`) that populates a **fabricated test account** with 18 months of realistic sample data by authenticating as that account and writing through the **real `sync_push` RPC and real sharing RPCs** — so every server-side invariant (CHECKs, triggers, RLS, role ladders) is exercised exactly as the app exercises it, and a fresh device install syncs the data down without rejections.

The tool is generic over several allowlisted test accounts (the Apple review account is one of them); each run seeds one target account plus its sharing partner.

## Hard requirements (from the issue, restated as decisions)

1. **Target safety.** Target email comes from `LUNARLOG_SEED_ACCOUNT_EMAIL`; it must be a member of `LUNARLOG_SEED_ALLOWLIST` (comma-separated). Refuse **before any write** (AC #2) — including account lookup-via-admin — if not allowlisted. Credentials/keys only from env (`.env` is fine; never committed, never printed). All names/data fabricated; no real people.
2. **Idempotent.** A gitignored local state file (suggest `.seed-state.json` at repo root; add to `.gitignore`) records what the tool created: per account — user id, profile ids, partner email. Re-running: the tool first verifies every profile the account owns or shares (RLS-scoped `profiles` + `profile_guardians` reads as the account) is in the state file; if any row is not tool-created it **refuses** (issue: "refuses if the account owns or shares a profile it didn't create"). Otherwise it resets by calling `public.delete_profile_data(p_profile_id)` (owner RPC; full purge incl. co-guardians' rows, connections, outbox — see facts) for each tool-created profile, then re-seeds. Never touches rows it didn't create.
3. **Write path = user session.** Sign in via `POST /auth/v1/token?grant_type=password` (http package, direct dep). All data writes go through `POST /rest/v1/rpc/sync_push` with the user's bearer token, and sharing via the RPCs below. The service key (`SUPABASE_SECRET_KEY`) is used **only** for: allowlist-independent guard queries are NOT allowed with it — specifically only (a) creating a missing account (`POST /auth/v1/admin/users`) and (b) setting a password identity on an existing allowlisted account that has none (so the Apple-review account, if it's Apple-sign-in-only, becomes password-authable; additive, doesn't break Apple sign-in). Nothing else.
4. **Account bootstrap.** If the target (or partner) email doesn't exist: create it via admin API with `LUNARLOG_SEED_PASSWORD` (shared fabricated password for test accounts; per-account override `LUNARLOG_SEED_PASSWORD_<UPPERCASE_SLUG>`). If it exists without a password identity: set one (service key, allowlisted emails only). `SUPABASE_URL` selects the environment; local validation uses `http://127.0.0.1:54321`.

## Content spec (default `--months 18`, flag-clamped to ≥12; `--seed <int>` for determinism)

Per target account, 2 profiles (3rd optional), fabricated names (e.g. "Maya", "Riley"):

- **Adult self profile**: `relationship: 'self'`, `birth_year ≈ 1988`, `is_minor: false`, `profiles.mode: 'standard'`, `profile_modes` row `mode: 'tracking'`, `bbt_unit: 'celsius'`, `weight_unit: 'kg'`.
- **Teen profile**: `relationship: 'daughter'`, `birth_year ≈ 2012`, `is_minor: true`, `profiles.mode: 'teen'`, `profile_modes` `mode: 'tracking'`, **`bbt_unit: 'fahrenheit'`, `weight_unit: 'lb'`** (covers "both display units").
- **Cycles**: 18 months with natural variation — cycle length 26–32d, period 4–6d, flow from the 7-value set (see facts; `spotting` flow is deprecated, never write it), spotting days as **observation rows** `category: 'spotting', code: 'spotting'`; 2 `cycle_overrides` (one `excluded_from_average`, one `manual_start`); current in-progress cycle (latest start ~2 weeks ago). Seed `last_period_start` / `typical_cycle_length_days` / `typical_period_length_days` on profiles to match.
- **Daily observations**: graded pain (`category: 'pain'`, taxonomy code, `intensity: 1–5`; mostly ≤3, a couple of 4s for realism), symptom/mood tags as observations with taxonomy codes (feelings/mind/energy/sleep/digestion…), the **#456 perimenopause cluster** occasionally on the adult (`hot_flashes, night_sweats, brain_fog, hrt, vaginal_dryness` under category wire `hot_flashes`), PMS days (`day_entries.pms: true` + tags), occasional notes (≤ `kMaxNoteLength`).
- **Numeric measurements**: BBT with a **biphasic curve** (follicular 36.3–36.6 °C, luteal +0.2–0.5 °C, ±noise; a few `excluded: true` outliers) — `category: 'bbt', code: null, unit` per profile pref (fahrenheit values converted via `lib/domain/models/measurement_unit.dart`); weight with slow drift (`category: 'weight', code: null`). One row per day per category (chart keys off cycle day; latest-updatedAt-wins per date).
- **Care notes** (~6) and **visit-prep items** (~10, some `is_checked: true` — server stamps check state from the caller; do NOT send `checked_by_user_id`/`checked_at`).
- **Reminder windows**: `upsert_reminder_window(p_profile_id, p_estimated_next_start, p_episode_open)` per profile from the generated cycle math (reuse `lib/domain/prediction` if trivially callable; else simple next-start arithmetic — either way deterministic).
- **Sharing** (uses the second fabricated account, `LUNARLOG_SEED_PARTNER_EMAIL`, also allowlist-enforced, must differ from target; created/bootstrapped the same way):
  - Guardian: `create_guardian_invitation` as owner (co_parent on the adult profile, caregiver on the teen), then sign in as partner and `accept_guardian_invitation`. **Token flow: the client generates the raw token and sends only `sha256(utf8(raw))` hex (`crypto` package); accept takes the same hash.** Defaults TTL is fine (accepted within the same run).
  - Prediction connection: `create_prediction_connection` on the **adult profile only** (the teen counts as a minor via `profile_counts_as_minor(is_minor, birth_year)` — refused by design), accept as partner.
- Do **not** set `notification_preferences` (default off keeps the outbox clean).

## sync_push facts you must respect (verified against `20260915200001_sync_push_tombstone_resurrection_guard.sql`, the current definition)

- Signature: `sync_push(p_profiles, p_day_entries, p_observations default [], p_profile_modes default [], p_cycle_overrides default [], p_care_notes default [], p_visit_prep_items default []) returns jsonb` → `{resolved, rejected, server_now}`. **Per-row failures land in `rejected` — the tool must assert `rejected == []` after every call and fail loudly otherwise.**
- Caps: **500 rows per array, 3500 total per call** → chunk into multiple calls (profiles → day_entries → observations → profile_modes → cycle_overrides → care_notes → visit_prep; children after parents; observations after their day entries).
- `updated_at` required on every row; **must be ≤ now+5min AND, for day_entries with an id the server has never seen, not older than now−180d** (tombstone-resurrection guard). So: backdate `local_date`/`observed_at` freely, but set every `updated_at` within the last ~170 days (spread realistically; a single recent timestamp for all rows is also valid and simpler — your call, tests pin whichever you choose).
- Key allowlists are strict (`c_profile_keys`, `c_day_entry_keys`, `c_observation_keys`, `c_profile_mode_keys`, `c_cycle_override_keys`, `c_care_note_keys`, `c_visit_prep_item_keys` in that file) — any unknown key rejects the row. **Do not send** `user_id`, `server_version`, `logged_by_user_id`, `last_modified_by_user_id`, `checked_by_user_id`, `checked_at` (tolerated-but-ignored or server-stamped; keep payloads minimal and exactly within the allowlists).
- `profile_modes` rows have **no `id` and no tombstones** (key = profile_id); every payload column behind `v_row ? 'key'` containment guards.
- One live `day_entries` row per `(profile_id, local_date)` (same-date resolver will tombstone losers — generate exactly one per day/profile). Live observations dedup on `(profile_id, local_date, category, code, source)` where `code` is non-null — never emit two live rows with the same day+category+code. `observations.local_date` is re-derived server-side from `observed_at at time zone tz` — set `tz` consistently (e.g. a fixed IANA zone per profile) and include `observed_at` (instant) for measurement rows; keep client-computed `local_date` consistent with it.
- `flow` values (wire): `none, not_bleeding, light, medium, heavy, super_heavy` (write `not_bleeding` for logged non-bleed days; never write deprecated `spotting` as flow). Tags: ≤32, each ≤64 chars, and use **real taxonomy codes only** (`lib/domain/tags.dart` `kTagTaxonomy` / `validateTagCodes`) so the app UI renders them.
- ULIDs via `lib/data/db/ulid.dart` (`UlidGenerator` — injectable clock/random; use a seeded `Random` for determinism). IDs must match `^[0-9A-HJKMNP-TV-Z]{26}$`.
- Import client constants rather than duplicating: `lib/domain/limits.dart`, `lib/domain/tags.dart`, `lib/domain/models/flow_level.dart`, `lib/domain/models/measurement_unit.dart`, `lib/domain/models/measurement_validation.dart` (BBT 34.0–42.0 °C, weight 10–300 kg after conversion).

## Determinism & idempotence details

- `--seed <int>` + injected fixed clock → byte-identical payload (digest test). Runtime uses real clock; state file tracks created ids per account.
- State file also records the run config (months, seed) so re-run with a different config is an explicit `--reset-and-reseed` rather than a surprise.

## Tests (AC #4)

- `test/tool/seed/…` (`flutter_test`, mirroring `test/tool/mutation_gate_test.dart`'s relative-import pattern; test-only exports where needed):
  - determinism: same seed + fixed clock → identical payload digest;
  - allowlist guard: non-allowlisted target → aborts with **zero** write calls (fake `http` client records calls);
  - row shapes: every emitted row passes a validator that mirrors the sync_push allowlists/limits above; flow ∈ 7-value set; tags pass `validateTagCodes`; all length caps;
  - chunking ≤500/array and ≤3500/call; `updated_at` policy window;
  - reset path: `delete_profile_data` invoked for exactly the state-file profiles; foreign-profile guard refuses.
